# Improvement Changelog

| Stage | What we tried and why | Evidence | Decision / Learning |
|---|---|---|---|
| Baseline | Naive keyword-matching over the scanner's own description text (mirrors what happens when an analyst trusts the scanner's wording at face value, with no independent check) | 5/10 (50%) accuracy against 10 known-correct labels. See "Iteration 1" row for the failure pattern. | Established the starting point -- this IS realistic: real scanners' free-text descriptions really do get taken at face value under time pressure. |
| Iteration 1 | Added a **tool** (local synthetic vulnerability knowledge base) so the agent looks up the finding's actual known-affected version range instead of parsing prose | Immediately fixed 3/3 version-mismatch false positives (case-02, case-04, case-09) that the baseline had wrongly confirmed just because the scanner's wording sounded confident | Kept. This is the single highest-value change -- version-range lookup alone recovers most of the gap. Confirms the core hypothesis: the real bottleneck is "no independent version check," not "bad wording parsing." |
| Iteration 2 | Added **verification**: split logic by vulnerability class -- version-dependent issues confirm on version match, but config-class issues (weak creds, no-auth) require direct exploitation evidence, not just a banner/open port | Fixed case-06/case-07 pair: two nearly-identical MySQL findings, one with only an open port (correctly downgraded to Needs Verification) and one with an actual successful login shown (correctly Confirmed) | Kept. Tried treating all vuln classes the same first -- that collapsed this exact pair to the same label, which is wrong; the config-class-vs-version-class distinction was necessary, not cosmetic. |
| Iteration 3 | First version of the evidence check required "direct proof of exploitation" for ALL vulnerability classes, including version-dependent ones | Broke case-01 and case-08 -- both are legitimate version-match confirmations where the only evidence is a banner grab, and requiring exploit-level proof wrongly downgraded them to Needs Verification | **Removed.** Learning: a version match is *itself* strong evidence for version-dependent vulns; treating it like a config-class issue (which genuinely needs behavioral proof) was over-applying one rule to two different problem shapes. |
| Iteration 4 | Added a narrower check: even with version match, look for evidence text that *contradicts* exploitability (e.g. "negotiated by default" showing a secure protocol is actually what's active) | Fixed case-05 (TLS 1.0 offered, but TLS 1.2 negotiated by default) without breaking case-01/case-03/case-08 | Kept. This is the "one challenging case" -- see README. It required distinguishing "version match" from "version match AND nothing in the evidence undercuts it." |
| Iteration 5 | Added session **memory** (dedupe by host+plugin within one run) | No accuracy change on this 10-case set (no duplicates in it by design), but prevents re-analyzing repeat findings across a real multi-host scan, which is the realistic use case this targets | Kept, though its value isn't visible in this particular eval set -- disclosed honestly rather than padding the metric. Would need a case with an intentional duplicate to actually exercise this path in eval. |
| Final | Combined all of the above | **10/10 (100%) accuracy**, up from baseline's 5/10 (50%) -- see `eval/results/latest.json` and the table in README | Main contribution: the version-range lookup (Iteration 1) recovered the most ground; the config-class vs. version-class split (Iteration 2) was necessary for correctness, not just polish. |
